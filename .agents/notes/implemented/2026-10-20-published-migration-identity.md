# Agent Note: 已发布 fork 迁移以完整文件名作为身份

Status: implemented
Kind: architecture
Protocol: agent-notes/v1

## 问题

本 fork 与上游曾共享迁移编号空间。同步上游时，相同数字前缀可能让人想把已发布的 fork 迁移重新编号，但运行中的数据库以完整文件名记录已执行版本；改名会改变身份，使已有 DDL 被再次执行。

本记录于 2026-10-20 根据当前代码和贡献指南整理。原始决策的完整讨论与时间未重新考证。

## 决策

保留已发布 fork 迁移的完整文件名和内容。新变化通过新迁移前进；新的 fork 迁移使用贡献指南约定的 9001–9099 范围。历史同号情况由精确冻结的清单处理，不能扩展该清单来接受新的碰撞。

当前规则由 [贡献指南](../../../CONTRIBUTING.md)、[版本提取代码](../../../server/internal/migrations/migrations.go) 和 [已发布迁移摘要检查](../../../server/internal/migrations/fork_history_test.go) 共同说明；具体操作以这些当前文件为准。

仓库另有 [458 改为 466 的专项索引兼容案例](../../../server/cmd/migrate/migrate_assignee_frequency_renumber_test.go)，使用幂等创建、保留旧账本及专门检查处理身份变化。该特例不授权批量重编号已发布 fork 迁移。

## 替代方案

重新编号已发布文件：贡献指南明确解释了身份变化会触发重复执行，因而保留原名。

不断扩展历史碰撞例外：现有摘要测试的注释明确将例外限制在首次上游同步前已发布的精确历史，要求后续变化采用新的唯一编号。更早的其他备选方案未从历史重建。

## 后果

历史迁移不会因同步整理而被当作新迁移重放。代价是仓库继续保留历史同号文件，以及一个有明确范围的历史摘要清单；新迁移必须遵守当前编号约定。
