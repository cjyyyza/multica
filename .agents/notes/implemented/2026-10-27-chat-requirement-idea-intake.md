# Agent Note: 聊天新建需求从想法开始

Status: implemented
Kind: feature
Protocol: agent-notes/v1

## 问题

聊天侧栏的「新建需求」先要求易协作来源 URL，再预览并绑定已有单据。这和 `/requirement <想法>` 不是同一条入口：后者用默认模板建一份待澄清草稿，标题取想法首行，然后在 Multica Chat 里澄清。来源 URL 作为第一步让人不知道该填什么。

## 决策

聊天和需求流程里的「新建需求」先收集想法和可分配且已绑定运行时的智能体，调用已有的 `POST /yixiezuo/drafts`。不传模板 URL，由服务端使用与无覆盖 `/requirement` 相同的默认模板。标题取去除空白后的首行，最多 120 个 Unicode 码位；正文是整段想法。幂等键属于这次提交，由仍挂载的对话框持有，关闭后再打开仍重试同一份；传输失败不会换成新键。服务端已记录失败后，再次提交使用新键。尚未确认时不能改想法或智能体；放弃后再写新想法，并说明可能重复建单。

只有草稿读取返回 `requirement_id` 后才关闭弹窗并打开需求 Chat。`unknown` 或 `needs_reconcile` 不自动再建草稿，成员贴上新单据链接做只读核对。已有单据预览仍留在「用已有单据链接」，不作为第一步；它继续直接创建 Requirement，不经过 bridge 建草稿。

侧栏入口是会话列表宽度的一行，不再使用收缩的描边按钮。

## 替代方案

完全去掉来源 URL：已知单据无法在聊天里开始需求，浏览器验收也会依赖外部建单，因此不采用。

继续把来源 URL 放在第一步，想法作为次要入口：这就是被替换的难懂流程，因此不采用。

聊天入口猜测某个 POPO 机器人的模板：工作区可以有多个机器人，猜错会建到错误模板，因此不传覆盖，交给服务端默认值。

## 后果

无模板覆盖的 `/requirement <想法>` 和聊天新建需求使用同一草稿入口。配置了自定义模板的机器人仍只影响该机器人的 POPO 命令。结果未确认时不能靠再点一次创建来恢复。

## 验证与限制

2026-10-27，[草稿表单测试](../../../packages/views/requirements/components/requirement-intake-dialog.test.tsx)覆盖想法建草稿、标题截断、未知结果不重复创建、失败换键、读取失败不解锁创建，以及关闭对话框后仍用同一幂等键重试。已有来源预览仍须可靠快照后才创建。[客户端契约测试](../../../packages/core/api/client-requirements.test.ts)覆盖草稿路由、幂等键和缺省模板省略。[浏览器验收](../../../e2e/requirement-idea-intake.spec.ts)跑通服务端草稿操作、bridge claim/complete、需求创建与自动开启澄清 Chat，并验证未确认结果下不再提交；同批需求流验收同步改到阶段轨与验收确认弹窗。浏览器验收用合成快照代替真实易协作建单，未对真实 bridge 做验收。冻结的桌面验收脚本仍按旧的来源 URL 步骤编写，且只针对已固定的提交运行。
