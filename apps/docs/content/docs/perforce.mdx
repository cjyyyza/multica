Multica lets agents work in an existing [Perforce](https://www.perforce.com/) Helix workspace. Perforce uses a separate `p4_depots` list and `perforce_depot` project resource, so a Helix port is never treated as a Git remote.

<Callout type="info">
Multica does not store a Perforce password. The daemon uses the host Helix login (`P4USER`, `P4TICKETS`, `P4CONFIG`). Run `p4 login` on that machine first.
</Callout>

## Bind an existing workspace

Attach two project resources:

- an `in_place` `local_directory` pointing at the P4 workspace root on this machine;
- a `perforce_depot` for the client's depot or stream.

```bash
multica project resource add <project-id> --type local_directory \
  --local-path 'D:\DJ' --daemon-id <daemon-id> --output json
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

The daemon resolves the client through the directory's `P4CONFIG` and verifies its Owner, Host, and Root. It does not create a task client or download another depot copy. A missing directory or unusable client fails preparation with a configuration error.

Manage workspace depots under **Settings → Code**, or with:

```bash
multica p4 registry list
multica p4 registry add --port perforce.example.com:1666 --depot //depot/project
multica p4 registry remove --port perforce.example.com:1666 --depot //depot/project
```

Each entry has a port and depot, plus an optional stream, description, and Swarm URL. A Git HTTP URL is not a valid P4 port.

## Use native P4

Once bound, the task receives the real `P4PORT`, `P4USER`, `P4CHARSET`, and `P4CLIENT`, and runs inside the existing workspace. Use the installed `p4` directly:

```bash
p4 edit Source/Foo.cpp
p4 add Source/New.cpp
p4 fstat -Ol Source/Foo.cpp
p4 changes -m 20 -s submitted
p4 sync --fresh
p4 submit -c 12345
```

Use the installed binary's `p4 help` as the command reference. Multica does not inject changelists, rewrite flags, or maintain a version-specific parameter allowlist. `multica p4` is not a native-command proxy; its `registry`, `changelist`, and `swarm` namespaces provide only Multica-specific integrations.

<Callout type="warn">
This is a trusted-agent mode. Multica does not restrict changelists, depot paths, submit/sync/unshelve, or native `p4` writes. The agent shares the person's workspace and should only touch files and changelists needed for its task.
</Callout>

## Changelists and 易协作 tickets

Multica no longer creates, reuses, or closes out a task changelist. Use native commands when needed:

```bash
p4 change -o
p4 edit -c 12345 Source/Foo.cpp
p4 shelve -c 12345
p4 submit -c 12345
```

When the task has an associated 易协作 ticket, the runtime brief provides it. Include `refs #<ticket>` in a new changelist description for traceability. A missing ticket does not block P4 operations; never invent one.

At task exit the daemon does not automatically revert, shelve, submit, or create a Swarm review. Before finishing, the agent should inspect `p4 opened`, clean up only unchanged files it opened in the task CL, and shelve with native `p4 shelve` when a pending review is needed. Never revert the whole shared client.

## Helix Swarm

Configure a Swarm origin on the workspace depot. `multica p4 swarm ...` is a separate Multica integration that uses the host Helix ticket and the configured origin. Requests do not follow redirects.

```bash
multica p4 registry add --port perforce.example.com:1666 --depot //depot/project \
  --swarm-url https://swarm.example.com
multica p4 swarm create --port perforce.example.com:1666 --depot //depot/project \
  --changelist 12345 --output json
multica p4 swarm reviews --port perforce.example.com:1666 --depot //depot/project --output json
multica p4 swarm show --port perforce.example.com:1666 --depot //depot/project --review 77 --output json
multica p4 swarm comment --port perforce.example.com:1666 --depot //depot/project \
  --review 77 --body "Looks good"
multica p4 swarm link --port perforce.example.com:1666 --depot //depot/project --review 77
```

In a bound workspace, Swarm commands may omit `--port`, `--depot`, and `--stream`; the daemon fills only those connection defaults from the binding. `swarm create` still requires an explicit `--changelist` and does not shelve first. Shelve a pending changelist with native `p4 shelve` when needed; a submitted changelist becomes a post-commit review. Created or linked reviews appear on the issue. In an issue task, `swarm create` and `swarm link` also associate the review's changelist with the issue.

## Changelists on an issue

The issue's Perforce changelist section supports manual linking and unlinking by number. An agent can explicitly associate a native CL without leaving the task:

```bash
multica p4 changelist link --changelist 12345
```

The daemon verifies that the CL belongs to the bound client and reports its current state. The daemon then polls linked CLs and Swarm reviews, reporting pending, shelved, submitted, and deleted states, including the new number assigned by a commit server after submission.

When every linked changelist is submitted and the issue has no linked pull request, Multica can advance the issue according to the existing automation setting. 易协作 publication summaries include the linked CLs and Swarm reviews.

Polling only contacts currently configured depots and never starts an `rsh:` process. Swarm webhook ingestion, CI status on review cards, and a mobile Perforce UI remain outside this version.
