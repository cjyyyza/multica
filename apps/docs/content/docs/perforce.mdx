Multica runs agents against [Perforce](https://www.perforce.com/) Helix depots. Git remotes stay in `workspace.repos` and `github_repo` resources. Perforce uses a separate `p4_depots` list and `perforce_depot` resources so an older daemon never tries to `git clone` a Helix port.

<Callout type="info">
Multica does not store a Perforce password. The daemon uses the host Helix login (`P4USER`, `P4TICKETS`, `P4CONFIG`). Sign in with `p4 login` on that machine first.
</Callout>

## Your workspace

| When a run can edit files | Where the files are |
|---|---|
| The project has an `in_place` local directory on the running daemon *and* a Perforce depot, and the daemon resolves a Helix client under that directory | Your own workspace, in one changelist per task |

A new Helix client is created so it can be synced, and syncing downloads the depot. Multica does not do that. If the directory is missing, or the client under it cannot be resolved, the run does not fall back to a task-scoped checkout.

**Agent submission is disabled by default.** The agent shelves its changelist for you to verify and submit, unless a human owner or admin enables submission for that depot.

## Add a workspace depot

Open **Settings → Code**. The Perforce section lists Helix depots the workspace may sync. Each depot has **Agent may submit**, **Agent may sync**, and **Agent may unshelve**, all off until you enable them. Sync updates the workspace that depot is already bound to and does not create a client.

Only workspace owners and admins can grant these permissions. Project resources inherit them from a matching port, depot, and stream in this catalog; an unmatched resource keeps all three disabled. Changes apply when the next run is claimed.

Each entry needs:

| Field | Required | Example |
|---|---|---|
| Port | Yes | `perforce.example.com:1666` or `ssl:perforce.example.com:1666` |
| Depot | Yes | `//depot/project` |
| Stream | No | `//depot/project/main` |
| Description | No | Game client |
| Swarm URL | No | `https://swarm.example.com` |

HTTP Git URLs are rejected as a port. You can also manage the list with `multica p4 list`, `multica p4 add`, and `multica p4 remove`.

## Attach a project resource

Open the project **Resources** panel and attach a Perforce depot already listed on the workspace, or paste port + depot. One project can mix Git repositories, a local directory, and Perforce depots.

```bash
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

Attaching a depot in the desktop app asks for this machine's workspace folder first, when the project does not already have one set to edit the folder directly. A run does not start without that directory.

An existing directory in parallel mode keeps its isolation. Use its execution-mode control to explicitly switch to direct editing before attaching the depot.

When a run is claimed, project `perforce_depot` resources become the P4 list. The workspace fallback is all-or-nothing: a project with no `github_repo` and no `perforce_depot` resource inherits both workspace lists, while a project carrying either kind inherits neither. A Perforce-only project therefore no longer picks up workspace Git repositories it was never meant to touch.

## Workspace mode

Attach two resources to the project: a `local_directory` in `in_place` mode pointing at your workspace root (the directory holding `p4config.txt`), and the `perforce_depot` whose stream that client works in.

```bash
multica project resource add <project-id> --type local_directory \
  --local-path 'D:\DJ' --daemon-id <daemon-id> --output json
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

The daemon resolves the client from that directory (`p4 set -q` plus `p4 info`, so `P4CONFIG` decides, not a global `P4CLIENT`) and accepts it only when it is yours and local: the client Owner is the daemon's `P4USER`, its Host is empty or this machine, and the local path is inside the client Root. If both resources are present but the client does not resolve or does not pass those checks, the run fails and says why — it never falls back to writing read-only files in place.

Point the local directory at the workspace root, not at a subdirectory that is itself in the depot. Multica writes run files (the runtime brief, `.multica/`, `.agent_context/`, skill files) next to the working directory, and a run fails rather than writing them into version control.

### The changelist and its ticket

The agent gets one pending changelist per task, created the first time it opens a file. Its description is:

```text
refs #<ticket> <issue title>

Multica: <ISSUE-KEY>
```

`refs #<ticket>` is the 易协作 ticket number. Multica reads it from the issue's import record, or from a `refs #123456` in the issue title or description.

<Callout type="warn">
Without a ticket the agent cannot open any file: `multica p4 edit` returns `ticket_required`. Add `refs #<ticket>` to the issue description and trigger the agent again. Multica never invents a number.
</Callout>

Re-running the same issue on the same client reuses the pending changelist, matched on the `Multica: <ISSUE-KEY>` trailer.

### What the agent can and cannot do

The agent opens files with `multica p4 edit` and adds new ones with `multica p4 add` (or `add-files`), and reads the changelist with `multica p4 status`. History is `multica p4 filelog` and `multica p4 describe -c <number>`. Everything it opens lands in the task changelist. Omit `--port` and `--depot`; the daemon fills both from the binding. Do not look up P4PORT and retry. Passing only one of them is forwarded, but a port spelling that does not match the binding is rejected.

The daemon refuses, with an explanation the agent has to report rather than work around:

| Refusal | Reason |
|---|---|
| `ticket_required` | the task has no 易协作 ticket |
| `opened_by_you` | the file is already open in one of your changelists, including the default one |
| `exclusive_locked` | someone else holds the `+l` lock |
| `exclusive_not_allowed` | a `+l` file on a depot that does not set `allow_exclusive` |
| `outside_task_change` | a revert, reconcile, or reopen aimed outside the task changelist |
| `action_not_allowed` | submit, sync, or unshelve without the corresponding permission |
| `not_in_workspace` | a path outside the client Root |

Raw `p4` writes are blocked in the agent's environment (`P4CONFIG` and `P4CLIENT` are pointed at names that do not exist), so `p4 edit`, `p4 sync`, and `p4 submit` fail there. Read history through `multica p4 filelog` and `multica p4 describe -c`. File state in this client is `multica p4 fstat`; changelist lists are `multica p4 changes`. Both print p4's own output and forward flags after the verb. Raw depot reads such as `p4 print` still work, but raw `p4 fstat` cannot see this client. This is a guardrail, not a security boundary: the real enforcement is in the daemon routes above.

One agent task runs per client at a time, so two tasks pointed at the same workspace are serialised rather than interleaved.

### When the task ends

Success, failure, or cancellation all run the same close-out for a pending changelist:

1. `revert -a` inside the task changelist, which returns files the agent opened but did not change;
2. an empty changelist has any old shelf removed and is then deleted;
3. otherwise the complete shelf is replaced with the current files (`shelve -r`, with `-p` on an edge server);
4. unless the depot sets `no_auto_review`, a Helix Swarm review is created and linked to the issue.

**Changed files stay open.** You verify in the editor and submit; the agent's final comment states what it changed, the changelist number, and how to check it. `multica p4 status` reports the same thing while a run is in flight.

If the agent was allowed to submit and has done so, Multica reads back the actual submitted number and file list, preserves the original number, and skips shelving. A failed receipt read is reported as a failure and never repeats the submit.

A close-out or report failure is shown as a task failure. The daemon retains the changelist receipt for retry after an HTTP failure or restart; it does not treat a missing server route as successful delivery. Status polling only connects to currently configured project/workspace depots and never starts an `rsh:` process.

Two depot switches change this, and are set through a JSON `--ref` payload on the resource: `allow_exclusive` lets agents open `+l` files, and `no_auto_review` turns off the automatic Swarm review.

## No task client

`multica p4 sync` updates the bound client, only when its depot enables `allow_sync`. With no file arguments it syncs the full client view, including stream imports. Named arguments must be individual files in an authorized depot; directories and `...` wildcards are rejected. Without that permission or a workspace binding, the daemon returns `action_not_allowed`. It never creates a task client or a separate depot copy. `-c`/`--changelist` and `--fresh` are rejected; a person selects historical revisions or resets the workspace.

## Edit, checkout, and shelve

In your workspace, agents open files through the daemon:

```bash
multica p4 edit --port perforce.example.com:1666 --depot //depot/project -- Source/Foo.cpp
multica p4 checkout --port perforce.example.com:1666 --depot //depot/project -- Source/Foo.cpp
multica p4 add --port perforce.example.com:1666 --depot //depot/project -- Source/New.cpp
multica p4 add-files -- Source/New.cpp
multica p4 filelog --output text -- Source/Foo.gbd
multica p4 describe -c 12345
multica p4 fstat -Ol -- Source/Foo.cpp
multica p4 changes -m 20 -s submitted
multica p4 change --port perforce.example.com:1666 --depot //depot/project --description "Fix the crash"
multica p4 shelve -c 12345 -f
multica p4 status --output json
```

`checkout` is an alias of `edit`; `changelist`, `changelists`, `rename`, and `update` are aliases of `change`, `changes`, `move`, and `sync`. `multica p4 add <files>` is `p4 add` (`add-files` is the same command). `multica p4 add` with no files still registers a depot. `-c` is `--changelist`. `revert -a` is `--unchanged`. `shelve -f` is `--force`. `move <source> <dest>` is the same as `--dest`. Other verbs: `delete`, `opened`, `reconcile` (`rec`), `reopen`. `reconcile -n` previews changes without creating or touching a task changelist. Exclusive-lock (`+l`) files must be edited before they can be written.

`multica p4 filelog -- <files>` prints each revision and its changelist description (`-L`, or the full text with `--long`). `--max` limits revisions (default 20, at most 200). It does not take `-c`. `multica p4 describe` with no number describes this task's changelist. `describe <number>` or `describe -c <number>` reads that changelist, including its description, only when every listed file is in this task's authorized depots. If those files cannot be confirmed, the description is not returned.

`multica p4 fstat`, `changes`, `files`, `dirs`, `grep`, `print`, `diff`, `diff2`, `annotate`, `where`, `have`, `sizes`, `integrated`, `interchanges`, and `resolved` run in the bound client and print p4's own output. Flags after the verb are forwarded with per-command value and rejection rules (`fstat -Ol`, `changes -m 20 -s submitted`, `diff -du3`, `print --offset 100 --size 50`). `-m` on `changes` defaults to 50 and cannot exceed 200. A `fstat` or `files` wildcard must name a subdirectory and include `-m`; a whole-depot wildcard is rejected. `dirs`, `grep`, `integrated`, and `interchanges` allow bounded subdirectory wildcards. `print`, `resolved`, and the other file reads require individual files. Connection flags, `print -o` (including `-ooutfile`), and unscoped branch/stream-view forms are rejected in separated and attached forms. Do not pass `--port` or `--depot`.

`multica p4 resolve` always injects this task's changelist and requires an automatic mode (`-as`, `-am`, `-af`, `-at`, or `-ay`) unless `-n` or `-N` previews the operation. It rejects caller-selected changelists and stream-spec resolves. With no file arguments, the injected changelist still prevents it from touching another changelist.

`opened` lists only this task's changelist. `multica p4 opened -F "%depotFile% %change%"` prints each file's depot path and changelist; `%change%` is the number or `default`, matching `p4 -ztag`, not the words `change N` from plain `p4 opened`. The flag may also precede the verb. `--output json` returns the same rows as `files`. Other p4 options are not forwarded, so `opened -a` and `-x` stay rejected.

`multica p4 submit` submits only this task's changelist and requires `allow_submit` from a human workspace administrator. Machine credentials cannot edit workspace depot settings. Before submitting, the daemon re-reads the pending client, owner, task marker and `refs #` ticket, reverts unchanged files, rejects an empty changelist, and deletes the whole shelf. Whole-shelf deletion preserves the associated Swarm review's files and link; Multica does not approve or archive it. Turning the switch off cannot undo a submission. `multica p4 unshelve` restores only this task's own shelf and requires `allow_unshelve`.

## Helix Swarm

Set a Swarm origin on the workspace depot (`--swarm-url` or the settings field). The daemon authenticates with the host Helix ticket (`p4 login`); Multica does not store a Swarm password.

Task commands use the configured depot URL. An explicit `--swarm-url` must match it. Swarm requests do not follow redirects; configure the final service URL.

```bash
multica p4 add --port perforce.example.com:1666 --depot //depot/project --swarm-url https://swarm.example.com
multica p4 swarm create --port perforce.example.com:1666 --depot //depot/project --changelist 12345 --output json
multica p4 swarm reviews --port perforce.example.com:1666 --depot //depot/project --output json
multica p4 swarm show --port perforce.example.com:1666 --depot //depot/project --review 77 --output json
multica p4 swarm comment --port perforce.example.com:1666 --depot //depot/project --review 77 --body "Looks good"
```

`swarm create` shelves the pending changelist first unless you pass `--no-shelve`. The task's submitted changelist becomes a post-commit review. Without a bound task workspace, use `--no-shelve`; Multica never operates an old task client.

A review created (or linked) during an issue task shows up on the issue: on its changelist card when Multica knows which changelist it reviews, and in the sidebar **Pull requests** section otherwise. Put the issue identifier (`DJ01-7`) in the Swarm description, or run `multica p4 swarm create` / `multica p4 swarm link` from that issue's task.

```bash
multica p4 swarm link --port perforce.example.com:1666 --depot //depot/project --review 77
```

If review creation succeeds but linking to the issue fails, the CLI prints the review receipt and exits with an error. Retry `swarm link` with that review ID instead of creating another review.

Depots are not prefetched; an enabled sync updates only the existing workspace.

## In this release

- In-place edits in your own client, one changelist per task, automatic revert-unchanged, shelve, and Swarm review
- No task-scoped client and no per-task depot sync
- Changelists on the issue: a Perforce changelists section, manual linking by number, and daemon polling that notices a submit — including the new number a commit server assigns
- Issue auto-advance once every linked changelist is submitted, on issues with no linked pull request

## Not in this release

- Swarm webhook ingestion and CI status on the review card
- Submitting without an owner or admin enabling it for the depot
- Reviewing someone else's changelist as a task
- Moving files the Unreal editor checked out into the task changelist from the UI (the run reports them instead)
- Create-project dialog P4 attach (attach after create)
- Mobile Perforce UI
- Landing-page marketing copy
