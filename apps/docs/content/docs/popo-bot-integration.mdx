POPO uses the shared conversation and task engine through the DJ01Bot TypeScript bridge on Windows. That process holds the POPO connection and talks to Multica over a workspace-scoped bridge token.

One dj01bot robot maps to one Multica agent. Use a stable `robot_id` from `~/.dj01bot/config.json` (`websocketRobots[].id`), or `default`.

## Before you start

- A workspace owner or admin mints a pairing code in Multica.
- Install the DJ01Bot TypeScript version and Node.js 22.5 or newer on Windows. From the DJ01Bot root, run `npm --prefix ts ci` and `npm --prefix ts run build`.
- Self-hosted servers set `MULTICA_POPO_ENABLED=true`.

<Callout type="info">
The Go command `multica popo gateway` is gone. Use `node ts/dist/multica-bridge.js`.
</Callout>

## 1. Pair the Windows bridge

1. In Multica, create a one-time pairing code (workspace owner/admin).
2. From the DJ01Bot root on Windows:

```bash
node ts/dist/multica-bridge.js pair --server https://your-multica.example --pairing-code <code>
node ts/dist/multica-bridge.js run --server https://your-multica.example
```

Pairing writes `{server, bridge_id, token, workspace_id}` under `%USERPROFILE%/.dj01bot/multica-bridge/`. Keep `run` going so heartbeats stay fresh (45s without a heartbeat is offline).

## 2. Connect a robot to an agent

1. Open **Agents**, select an agent, then **Integrations**.
2. Choose an online Windows bridge and an idle robot (`connected` and not occupied by dj01bot/Sparse).
3. Click **Connect**.

A robot can belong to only one live Multica agent.

## First use and account binding

The first time a member messages the robot, it sends a single-use Multica account-binding link (`/popo/bind?token=`). Open it, sign in to the same workspace, then send the message again. The link expires after 15 minutes.

## Use the robot

### Private chats

Send text directly. No @-mention is required.

### Groups

Mention the robot in a group to send it a request. Quoting a known task reply can add a comment to that same task. Media attachments and Windows QR registration are supported by the corresponding bridge flows.

Once a run starts, its Multica reply card shows progress and the final state. Receiving a message does not add an ING sticker: transport acceptance does not mean execution has started.

### Commands

Ordinary chat is the default for new account bindings. Existing bindings on robots with a configured requirement template retain their previous requirement-entry default during upgrade until the member explicitly selects a mode. Each member chooses their mode independently for each private chat or group. The robot's requirement template only supplies a default source template. In groups, each Multica member has a separate model conversation. Automatic group history is excluded; explicitly selected quotes and forwards remain available as input. Messages and replies posted to the group remain visible there. Personal mode controls and requirement queries reply privately to the sender.

| Command | Action |
| --- | --- |
| `/mode`, `/help` | Show your mode or command help |
| `/mode chat`, `/chat` | Select ordinary chat |
| `/mode requirement`, `/requirement` | Select the requirement flow and show your current requirement |
| `/requirement new [template-url] <idea>` | Create an independent requirement draft |
| `/requirement status [requirement-id]` | Read the requirement stage and next step |
| `/requirement list` | List recent requirements you participate in for this agent |
| `/requirement open <requirement-id>` | Select an accessible requirement and return its Chat or issue link |
| `/requirement resolve <operation-id> <new-issue-url>` | Read back an unconfirmed source draft |

Requirement intake needs the member's own 易协作 bridge. Clarification and approval happen in Multica Chat; execution and later changes use its single linked issue, followed by human acceptance. Multica labels requirement conversations and shows the current stage and next step. Requirement Chat access follows participant roles; the resulting issue keeps workspace issue permissions.

- `/new [message]` starts a new ordinary Chat in chat mode, or an independent requirement in requirement mode. `/clear` resets an ordinary Chat's context.
- `/issue <title>` creates a Multica issue (`origin_type=popo_chat`).
- `/reply ISSUE-123 <comment>`, `/status ISSUE-123` and `/stop ISSUE-123` operate on an existing task. Stopping a run keeps task status separate.
- `/yixiezuo preview <issue-url>` queues a single-source preview. Keep `multica yixiezuo bridge --workspace-id <workspace-uuid>` running under the same Multica member account that is bound to the sender.
- `/yixiezuo show <operation-id>` displays source material or the operation result.
- `/yixiezuo import <issue-url> [--project <project-uuid>]` imports one source issue directly. The local bridge reads it, then the bot reports success or failure in this chat. The task stays unassigned and no agent run starts. Repeated import preserves the existing task and any existing notification route.
- `/yixiezuo import <preview-id> --confirm --project <project-uuid>` imports after an explicit preview.
- `/yixiezuo refresh ISSUE-123` updates the source snapshot while preserving local task fields.
- `/yixiezuo publish ISSUE-123 [--status <source-status>]`, followed by a result summary on the next line, prepares a review. `/yixiezuo confirm <review-id>` queues the reviewed write. Confirmation expires after 15 minutes and is bound to the same member, robot, chat, task revision and source snapshot.

The selected project can carry a `perforce_depot` resource. After a member assigns the imported task, the run receives that project's P4 context. Task comments and run results return through the original chat; publishing a result to 易协作 remains an explicit confirmation step.

## Manage connections

**Settings → Integrations → POPO** lists bridges and robots. Each member can see their own POPO account binding on each robot, open the private-chat binding instructions, and unlink their account. Unlinking keeps Chat and requirement history but clears that robot's personal mode selections. Owners and admins can revoke a bridge token immediately. Disconnecting a robot stops inbound/outbound for that agent but keeps Multica conversations.

## Self-hosting setup

```dotenv
MULTICA_POPO_ENABLED=true
```

Unset or any value other than `true` hides the management APIs (`configured: false`) and returns `503 popo_not_configured` on the Windows bridge routes.

`popo-cli` is a logged-in user identity used by other Windows tools. It is not this robot channel.
