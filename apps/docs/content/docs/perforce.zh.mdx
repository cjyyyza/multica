Multica 可以让智能体在 [Perforce](https://www.perforce.com/) Helix 工作区里干活。Perforce 使用独立的 `p4_depots` 列表和 `perforce_depot` 项目资源，不会把 Helix port 当成 Git 地址。

<Callout type="info">
Multica 不保存 Perforce 密码。守护进程使用本机 Helix 登录（`P4USER`、`P4TICKETS`、`P4CONFIG`）。请先在那台机器上执行 `p4 login`。
</Callout>

## 绑定现有工作区

项目需要两条资源：

- `in_place` 的 `local_directory`，指向本机 P4 工作区根目录；
- `perforce_depot`，对应这个 client 的 depot 或 stream。

```bash
multica project resource add <project-id> --type local_directory \
  --local-path 'D:\DJ' --daemon-id <daemon-id> --output json
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

守护进程通过目录内的 `P4CONFIG` 解析 client，并核对 Owner、Host 和 Root。Multica 不创建任务专用 client，也不为任务另下载一份 depot。缺少目录或无法解析 client 时，运行会给出配置错误。

工作区 depot 在 **设置 → 代码** 中管理，也可以使用：

```bash
multica p4 registry list
multica p4 registry add --port perforce.example.com:1666 --depot //depot/project
multica p4 registry remove --port perforce.example.com:1666 --depot //depot/project
```

每条 depot 包含 port、depot，以及可选的 stream、描述和 Swarm URL。Git HTTP URL 不能作为 P4 port。

## 使用原生 P4

绑定成功后，任务获得真实的 `P4PORT`、`P4USER`、`P4CHARSET` 和 `P4CLIENT`，工作目录就是现有工作区。可以直接使用本机安装的 `p4`：

```bash
p4 edit Source/Foo.cpp
p4 add Source/New.cpp
p4 fstat -Ol Source/Foo.cpp
p4 changes -m 20 -s submitted
p4 sync --fresh
p4 submit -c 12345
```

具体参数以本机 `p4 help` 为准。Multica 不注入 changelist、不重写 flag，也不维护 P4 版本参数白名单。`multica p4` 不是原生命令代理，只保留 `registry`、`changelist` 和 `swarm` 三个 Multica 自有集成命名空间。

<Callout type="warn">
这是可信智能体模式。Multica 不限制 changelist、depot 路径或 submit/sync/unshelve，也不阻止原生 `p4` 写操作。智能体与人共用同一个工作区，应避免触碰任务之外的文件和 changelist。
</Callout>

## Changelist 与易协作单号

Multica 不再自动创建、复用或收尾任务 changelist。需要时使用原生命令：

```bash
p4 change -o
p4 edit -c 12345 Source/Foo.cpp
p4 shelve -c 12345
p4 submit -c 12345
```

如果任务关联了易协作工单，运行说明会提供单号；创建 CL 时可在描述中写 `refs #<单号>` 便于追溯。没有单号不会阻止 P4 操作，也不要编造单号。

任务结束时，daemon 不自动 revert、shelve、submit 或创建 Swarm review。Agent 收尾前应检查 `p4 opened`，只清理自己在任务 CL 中打开但未修改的文件；需要 pending review 时用原生 `p4 shelve`，不要对整个共享 client 执行 revert。

## Helix Swarm

在 workspace depot 上配置 Swarm 地址。`multica p4 swarm ...` 是独立的 Multica 集成，使用本机 Helix ticket 访问配置的 Swarm，不会跟随重定向。

```bash
multica p4 registry add --port perforce.example.com:1666 --depot //depot/project \
  --swarm-url https://swarm.example.com
multica p4 swarm create --port perforce.example.com:1666 --depot //depot/project \
  --changelist 12345 --output json
multica p4 swarm reviews --port perforce.example.com:1666 --depot //depot/project --output json
multica p4 swarm show --port perforce.example.com:1666 --depot //depot/project --review 77 --output json
multica p4 swarm comment --port perforce.example.com:1666 --depot //depot/project \
  --review 77 --body "Looks good"
multica p4 swarm link --port perforce.example.com:1666 --depot //depot/project --review 77
```

在已绑定的工作区中，Swarm 命令可以省略 `--port`、`--depot` 和 `--stream`，daemon 只从绑定中补全这些连接默认值。`swarm create` 仍必须显式传入 `--changelist`，且不会先 shelve。需要 pending review 时，先用原生 `p4 shelve`；已提交 CL 则创建 post-commit review。创建或关联成功后，review 会显示在任务上。在任务上下文中，`swarm create` 和 `swarm link` 还会把对应的 changelist 关联到当前任务。

## 任务上的 changelist

任务详情的 Perforce changelist 区域支持按编号手动关联和取消关联。

点击 CL 编号或文件数，可查看文件列表和文本差异。有搁置版本时显示该版本，提交后显示已提交版本，未搁置时读取本地工作副本。本地工作文件仅机器所有者可见。二进制文件仅显示文件信息；较大的差异会标明截断。读取需要已更新且在线的守护进程，并能访问项目配置的 Perforce 服务器。

Agent 也可以在任务中显式关联原生 CL：

```bash
multica p4 changelist link --changelist 12345
```

daemon 会校验 CL 是否属于当前绑定的 client，并上报当前状态。随后 daemon 轮询已关联 CL 和 Swarm 状态，识别 pending、shelved、submitted、deleted，以及 commit server 提交后改号的新编号。

当任务关联的 CL 全部已提交、且任务没有关联 Pull Request 时，Multica 可以按现有设置自动推进任务状态。易协作回写摘要也会带上已关联的 CL 和 Swarm 信息。

轮询只连接当前配置的 depot，不启动 `rsh:` 进程。Swarm webhook、review 卡片 CI 状态和移动端 Perforce 界面仍未包含。
