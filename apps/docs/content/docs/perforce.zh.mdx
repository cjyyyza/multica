Multica 可以让智能体在 [Perforce](https://www.perforce.com/) Helix depot 上干活。Git 远程仍写在 `workspace.repos` 和 `github_repo` 资源里。Perforce 使用单独的 `p4_depots` 列表和 `perforce_depot` 资源，避免旧版守护进程把 Helix port 当成 Git 去 clone。

<Callout type="info">
Multica 不保存 Perforce 密码。守护进程使用本机 Helix 登录（`P4USER`、`P4TICKETS`、`P4CONFIG`）。请先在那台机器上执行 `p4 login`。
</Callout>

## 两种模式

| 模式 | 什么时候走这条路 | 文件在哪里 |
|---|---|---|
| **工作区模式** | 项目同时挂了本机守护进程上的 `in_place` 本地目录**和** Perforce depot，并且守护进程能在该目录下解析出 Helix client | 你自己的工作区，每条任务一个 changelist |
| **任务 client 模式** | 其余情况 | 本次运行目录下的 `p4/` 子目录 |

工作区模式是大体量 Unreal depot 唯一可行的方式：300GB 的工作区不可能为每条任务同步一份，所以智能体直接在你已有的工作区里干活。

**两种模式下智能体都不提交。** 智能体只负责 shelve；你在编辑器里验证后用 P4V 或自己的脚本提交。

## 添加工作区 depot

打开 **设置 → 代码**。Perforce 一栏列出工作区可以同步的 Helix depot。

每条需要：

| 字段 | 必填 | 示例 |
|---|---|---|
| Port | 是 | `perforce.example.com:1666` 或 `ssl:perforce.example.com:1666` |
| Depot | 是 | `//depot/project` |
| Stream | 否 | `//depot/project/main` |
| 描述 | 否 | 游戏客户端 |
| Swarm URL | 否 | `https://swarm.example.com` |

HTTP 形式的 Git URL 不能当作 port。也可以用 `multica p4 list`、`multica p4 add`、`multica p4 remove` 管理列表。

## 关联项目资源

打开项目的 **资源**，从工作区已有 depot 里选一条，或填写 port 和 depot。同一个项目可以同时关联 Git 仓库、本地目录和 Perforce depot。

```bash
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

认领执行时，项目上的 `perforce_depot` 会成为 P4 列表。工作区回退是全有或全无：项目上既没有 `github_repo` 也没有 `perforce_depot` 时，两类工作区资源一起继承；只要挂了其中任何一类，两类都不再继承。这样只配 Perforce 的项目不会再拿到本来用不上的工作区 Git 仓库。

## 工作区模式

给项目挂两条资源：一条 `in_place` 的 `local_directory`，指向你的工作区根目录（放着 `p4config.txt` 的那一层）；一条 `perforce_depot`，对应这个 client 所在的 stream。

```bash
multica project resource add <project-id> --type local_directory \
  --local-path 'D:\DJ' --daemon-id <daemon-id> --output json
multica project resource add <project-id> --type perforce_depot \
  --port perforce.example.com:1666 --depot //depot/project --output json
```

守护进程在这个目录下解析 client（执行 `p4 set -q` 和 `p4 info`，由 `P4CONFIG` 决定，不读全局 `P4CLIENT`），并且只接受属于你本人、本机的 client：Owner 等于守护进程的 `P4USER`，Host 为空或等于本机，本地路径在 client Root 之内。两条资源都在、但 client 解析不出来或校验不通过时，运行直接失败并说明原因，绝不退回到“直接写只读文件”。

本地目录要指向工作区根目录，不要指向本身就在 depot 里的子目录。Multica 会在工作目录旁写入运行文件（运行说明、`.multica/`、`.agent_context/`、skill 文件），一旦这些路径属于版本控制，运行会直接失败，而不会把它们写进 depot。

### changelist 和单号

智能体每条任务拿到一个待提交 changelist，在第一次打开文件时创建。描述格式为：

```text
refs #<单号> <任务标题>

Multica: <任务编号>
```

`refs #<单号>` 是易协作工单号。Multica 从任务的导入记录里读，或者从任务标题、描述里的 `refs #123456` 里读。

<Callout type="warn">
没有单号时，智能体一个文件都打不开：`multica p4 edit` 返回 `ticket_required`。请在任务描述里补上 `refs #<单号>`，再重新触发智能体。Multica 不会编造单号。
</Callout>

同一条任务在同一个 client 上再次执行时，会按描述里的 `Multica: <任务编号>` 找回原来的待提交 changelist 继续用。

### 智能体能做什么、不能做什么

智能体用 `multica p4 edit` 打开文件、用 `multica p4 add-files` 新增文件，用 `multica p4 status` 查看 changelist。打开的文件都会进这条任务的 changelist。这个模式下 `--port` 和 `--depot` 可以省略。

守护进程会拒绝下面这些操作，并给出原因 —— 智能体必须把原因报出来，而不是绕过去：

| 拒绝原因 | 含义 |
|---|---|
| `ticket_required` | 这条任务没有易协作单号 |
| `opened_by_you` | 文件已经在你自己的某个 changelist（含 default）里打开 |
| `exclusive_locked` | 别人持有 `+l` 独占锁 |
| `exclusive_not_allowed` | `+l` 文件，而该 depot 没有开 `allow_exclusive` |
| `outside_task_change` | revert、reconcile 或 reopen 的目标在任务 changelist 之外 |
| `action_not_allowed` | submit、sync 或 unshelve |
| `not_in_workspace` | 路径在 client Root 之外 |

智能体进程里的原生 `p4` 写操作已被屏蔽（`P4CONFIG` 和 `P4CLIENT` 指向不存在的名字），`p4 edit`、`p4 sync`、`p4 submit` 在那里都会失败。只读查询 —— `p4 files`、`p4 print`、`p4 filelog`、`p4 describe`、`p4 changes` —— 照常可用，智能体靠它们读历史。这只是护栏，不是安全边界：真正的约束是上面那些守护进程检查。

同一个 client 上同时只跑一条智能体任务，指向同一个工作区的两条任务会串行执行，不会交叉。

### 任务结束时

成功、失败、取消都走同一套收尾：

1. 在任务 changelist 上执行 `revert -a`，把“打开了但没改”的文件退回去；
2. changelist 变空时，先清理旧 shelf，再删除 changelist；
3. 否则用当前文件完整替换 shelf（`shelve -r`，edge 服务器上加 `-p`）；
4. 除非 depot 设了 `no_auto_review`，否则自动建一个 Helix Swarm review 并关联到任务。

**改过的文件保持打开状态。** 你在编辑器里验证后提交；智能体的最终评论会写清改了什么、changelist 号，以及怎么验证。运行过程中用 `multica p4 status` 看到的也是这些信息。

收尾或上报失败会显示为任务失败。守护进程会保留 changelist 上报记录，在 HTTP 失败或重启后重试；服务端缺少上报接口也不会被当成投递成功。状态轮询只连接项目或工作区当前配置的 depot，不启动 `rsh:` 进程。

两个 depot 开关会改变上述行为，通过资源上的 JSON `--ref` 设置：`allow_exclusive` 允许智能体打开 `+l` 文件，`no_auto_review` 关掉自动 Swarm review。

## 执行中同步（任务 client 模式）

智能体用任务 CLI 同步，而不是直接连 Helix：

```bash
multica p4 sync --port perforce.example.com:1666 --depot //depot/project
multica p4 sync --port perforce.example.com:1666 --depot //depot/project --stream //depot/project/main
multica p4 sync --port perforce.example.com:1666 --depot //depot/project --fresh
```

守护进程会创建短的任务级 client（`mc` + 16 位十六进制），在任务根目录的 `p4/<client>` 里执行 `p4 sync`，并返回该路径。从子目录执行命令时，同步位置保持不变。client 和目录同时区分服务器、depot、stream 和运行。`--fresh` 会先删除上次的同步目录，再强制下载文件，避免服务器仍保留 have list 时返回空目录。本机 `PATH` 里需要有 `p4`。

使用 `--output json` 读取 `path` 和 `client`。client 使用 `noallwrite`，文件在 `edit` 之前是只读的。不要用本机默认 client 去跑 `p4`。

## 编辑、checkout 与 shelve

同步之后，先进入返回的 checkout 路径，再使用相对文件路径。通过同一个守护进程 client 打开文件：

```bash
multica p4 edit --port perforce.example.com:1666 --depot //depot/project -- Source/Foo.cpp
multica p4 checkout --port perforce.example.com:1666 --depot //depot/project -- Source/Foo.cpp
multica p4 add-files --port perforce.example.com:1666 --depot //depot/project -- Source/New.cpp
multica p4 change --port perforce.example.com:1666 --depot //depot/project --description "Fix the crash"
multica p4 shelve --port perforce.example.com:1666 --depot //depot/project --changelist 12345
multica p4 status --output json
```

`checkout` 是 `edit` 的别名。`multica p4 add` 仍然是往工作区登记 depot；新增文件用 `add-files`（即 `p4 add`）。其他命令：`delete`、`revert`、`opened`、`reconcile`（`rec`）、`move --dest`、`reopen --changelist`、`describe`。独占锁定（`+l`）的文件必须先 edit 才能写。

没有 `multica p4 submit` 这个命令。智能体只 shelve，由人验证后提交。

## Helix Swarm

在工作区 depot 上填写 Swarm 地址（`--swarm-url` 或设置页）。守护进程用本机 Helix ticket（`p4 login`）访问 Swarm；Multica 不保存 Swarm 密码。

任务命令使用 depot 已配置的地址，显式传入的 `--swarm-url` 必须与其一致。Swarm 请求不跟随重定向，请配置最终服务地址。

```bash
multica p4 add --port perforce.example.com:1666 --depot //depot/project --swarm-url https://swarm.example.com
multica p4 swarm create --port perforce.example.com:1666 --depot //depot/project --changelist 12345 --output json
multica p4 swarm reviews --port perforce.example.com:1666 --depot //depot/project --output json
multica p4 swarm show --port perforce.example.com:1666 --depot //depot/project --review 77 --output json
multica p4 swarm comment --port perforce.example.com:1666 --depot //depot/project --review 77 --body "Looks good"
```

`swarm create` 会先 shelve 待提交 changelist，除非传入 `--no-shelve`。已提交的 changelist 会建成 post-commit review。

在任务里创建或 `link` 的 review 会出现在任务上：Multica 知道它评审的是哪个 changelist 时，显示在对应的 changelist 卡片上；否则显示在侧栏的 **Pull Request** 区域。把任务编号（如 `DJ01-7`）写进 Swarm 说明，或在该任务的运行中执行 `multica p4 swarm create` / `multica p4 swarm link`。

```bash
multica p4 swarm link --port perforce.example.com:1666 --depot //depot/project --review 77
```

如果 review 创建成功但关联任务失败，CLI 会输出 review 回执并返回错误。使用该 review ID 重试 `swarm link`，无需重新创建 review。

不会预先拉取 depot。Helix 树可能很大，只在智能体请求时同步。

## 本版包含

- 工作区模式：在你自己的 client 里原地改文件，每条任务一个 changelist，自动退回未改动的文件、shelve 并建 Swarm review
- 任务 client 模式，并加了体积预检：depot 大到同步不了时直接拒绝，并提示改用工作区模式
- 任务上的 changelist：Perforce changelist 区域、按号手动关联，以及守护进程轮询识别提交 —— 包括 commit server 改号后的新号
- 关联的 changelist 全部提交、且任务上没有关联 Pull Request 时，自动推进任务状态

## 本版未包含

- Swarm webhook 接入、review 卡片上的 CI 状态
- 智能体提交 —— 这是设计决定，见[上面的两种模式](#两种模式)
- 把别人的 changelist 作为任务来评审
- 在界面上把 Unreal 编辑器自动 checkout 的文件移进任务 changelist（本版只在运行结果里报出来）
- 创建项目对话框里直接挂 P4（创建后再关联）
- 移动端 Perforce 界面
- 官网营销文案
